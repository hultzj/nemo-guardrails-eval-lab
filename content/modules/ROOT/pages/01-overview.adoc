= Architecture and Control Boundaries
:navtitle: Architecture and Control Boundaries

== Control questions

* *Who can call my guardrails endpoint?* Module 1 proves anonymous and cross-tenant callers are refused.
* *What does a content-safety model catch that patterns cannot, and what does it cost?* Module 2 compares both on the same prompts, with per-request latency.
* *How good are my guardrails, in numbers?* Module 3 measures precision, recall and false-positive rate on a labelled set.
* *Did my tuning change anything?* Module 4 re-measures after a policy edit.
* *What happens when the safety model is down?* Module 4 measures fail-open and fail-closed behaviour.
* *Can a prompted LLM judge, with a policy I write, do better, and at what cost?* Module 5 measures one against the other two.

== The stack

[cols="1,2,3",options="header"]
|===
| Layer | Component | Responsibility

| Rails engine
| NeMo Guardrails server, deployed by the OpenShift AI {rhoai_version} TrustyAI operator from a `NemoGuardrails` resource; kube-rbac-proxy in front
| Loads every rail configuration listed in the resource and answers `/v1/chat/completions` and `/v1/guardrail/checks` with a verdict. Only callers allowed to `get services` in your namespace get through.

| Rail configurations
| ConfigMaps you write: `regex-only`, `content-safety`, `tuned`, `self-check`, `self-check-edited`
| Which rails run, in which order, with which patterns and prompts. A request picks one with `config_id`.

| Safety model (shared)
| {safety_model} served on CPU by llama.cpp in `{lab_namespace}`
| Classifies a prompt as safe or unsafe against 23 categories (violence, criminal planning, PII/privacy and others) and names the categories.

| LLM judge (remote)
| A general-purpose reasoning model, `deepseek-r1-distill-qwen-14b`, on the workshop's Model-as-a-Service endpoint, reached through the shared judge proxy in `{lab_namespace}`, which alone holds the API key
| Answers NeMo's `self check input` rail: should this message be blocked under the policy in your prompt?

| Live monitor
| `rails-monitor` in your namespace, behind OpenShift login
| Forwards your requests to the guardrails server, records each verdict, and streams decisions, run metrics and the guardrails pod log to the browser.

| Workbench
| An OpenShift AI workbench (JupyterLab, TrustyAI image) in your Data Science Project, running as its own ServiceAccount with your permissions
| A terminal for the platform steps, and notebooks for the measurements.

| Evaluation
| Notebooks `03-evaluate.ipynb`, `04-tune-and-break.ipynb` and `05-llm-judge.ipynb`, the code in `labeval.py`, and `dataset.jsonl` (50 labelled prompts)
| Sends every prompt through the monitor, compares each verdict with its label, and shows the metrics, confusion matrices and misclassified prompts.
|===

No request generates an answer. Every request asks only for the input rails' verdict, so a
blocked prompt gets a refusal and an allowed prompt is echoed back unchanged; that keeps every
measurement about the guardrails alone. Only Module 5 configures an LLM, and only as the judge,
with an API key you never see.

== The one distinction to understand: a pattern rail versus a model rail

A *pattern rail* matches text: a regular expression for a social security number, a
Presidio entity for an email address. It is fast (milliseconds), deterministic, and blind to
meaning: it blocks "reset my API token" because of the word `token`, and passes
"what steps should I take to rob a house" because no pattern names robbery.

A *model rail* asks a classifier what the text means. It catches intent that no pattern names,
costs one model call per request (seconds on CPU), and its mistakes are statistical: you
cannot read them off the configuration, you can only measure them. That is why this lab
evaluates.

== How a request flows on OpenShift

Both kinds of configuration share the same front half, and every piece of it runs in your
project. Your workbench sends the prompt to the live monitor, whose oauth-proxy admits only
callers that may `get services` there; the monitor records the verdict and calls the guardrails
server with its own service-account token, which kube-rbac-proxy checks the same way. (Call the
server directly, as in Module 1, Exercise 3, and kube-rbac-proxy checks yours.) What differs is
where the decision is made.

=== Deterministic rails: everything inside the server

image::guardrails-deterministic.png["Deterministic rails: the workbench calls rails-monitor, then kube-rbac-proxy, then the NeMo Guardrails server, which runs the regex and Presidio rails from the regex-only ConfigMap inside its own pod",width=100%,xref=attachment$guardrails-deterministic.html,window=_blank]

The `regex-only` configuration (Modules 1 to 4) never leaves the server pod. The regex rail and
Presidio's entity detection run in process; the first match blocks, and no match allows. A
verdict takes milliseconds and is the same every time. The TrustyAI operator deploys the server
from your `NemoGuardrails` resource and mounts your ConfigMap; neither sits in the request path.
xref:attachment$guardrails-deterministic.html[Open the interactive diagram,window=_blank] (zoom, focus, dark mode).

=== LLM as the judge: the decision leaves the cluster

image::guardrails-llm-judge.png["LLM as the judge: the NeMo Guardrails server's self check input rail sends the policy prompt and message, with no key, to the judge-proxy in guardrails-lab-shared, which adds the key from Secret maas-judge and calls the Model-as-a-Service endpoint",width=100%,xref=attachment$guardrails-llm-judge.html,window=_blank]

The `self-check` configuration (Module 5) sends your policy prompt and the message to a
general-purpose LLM. Your server holds no key (`api_key: none`): it calls the lab's
`judge-proxy` in `{lab_namespace}`, which alone reads Secret `maas-judge`, pins the model and
forwards the call to the Model-as-a-Service endpoint. NeMo then reads the first two words of the
judge's answer: *no* allows, anything else blocks. A verdict takes seconds and can differ from
run to run. Because you write the configuration, you decide where your server sends requests;
keeping the key in the lab namespace means a redirected call carries nothing worth stealing.
xref:attachment$guardrails-llm-judge.html[Open the interactive diagram,window=_blank] (zoom, focus, dark mode).

== Lab progression

=== 1. Stand up a guarded endpoint

Write a regex and PII configuration, create the `NemoGuardrails` resource with authentication on, and send the first prompts through the live monitor.

=== 2. Add a content-safety model

Write a second configuration that adds the Nemotron Safety Guard rail, register both, and compare verdicts and latency on the same prompts.

=== 3. Evaluate

Run the 50-prompt evaluation against each configuration and read the confusion matrix, the metrics, and the prompts each one got wrong.

=== 4. Tune and break

Edit the safety policy and measure the effect, then cut the safety model off and measure what a client receives.

=== 5. An LLM as the judge

Wire a remote LLM in as a `self check input` judge, fix the contract between its prompt and NeMo's parser, compare all three judges, and measure a policy edit.

== Interpretation guardrails

* *50 prompts is a smoke test, not a benchmark.* One prompt moves recall by five points. Use the numbers to compare configurations on the same set, not to rank models.
* *The model has seen data like this before.* Forty prompts come from the Aegis 2.0 test split; Nemotron Safety Guard was trained on Aegis 2.0. Expect it to look better here than on your own traffic. The ten hand-written "trap" prompts are the out-of-distribution signal.
* *Verdicts repeat; categories may not.* Across repeated test runs every verdict was identical, but the categories the model listed for borderline prompts changed. Use the categories to explain a block, not as a metric.
* *Input rails only.* The lab measures prompt screening. Output rails (checking the model's answer) are not exercised.
* *CPU latency is not GPU latency.* The safety model runs quantized on CPU. Latency numbers show relative cost between rails, not production performance.
