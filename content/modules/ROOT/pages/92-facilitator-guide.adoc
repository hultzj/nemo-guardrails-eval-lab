= Facilitator Guide
:navtitle: Facilitator Guide

For facilitators provisioning lab environments ahead of class. Participants
can skip this page.

== Cluster prerequisites

This lab runs on one shared cluster: every participant, and the presenter, gets a namespace
`<username>{tenant_suffix}`. Check each prerequisite as cluster-admin:

[cols="2,3",options="header"]
|===
| Prerequisite | Check

| OpenShift {ocp_version} with OpenShift GitOps
| `oc get csv -n openshift-gitops-operator`

| OpenShift AI {rhoai_version} with the TrustyAI and Workbenches components `Managed`, and the TrustyAI workbench image
| `oc get crd nemoguardrails.trustyai.opendatahub.io notebooks.kubeflow.org` and `oc -n redhat-ods-applications get is odh-trustyai-notebook`

| A worker with 32 free CPU cores and 24 GiB free memory for the two safety-model replicas (16 cores each; tested on an m5.metal)
| `oc describe nodes \| grep -A5 'Allocated resources'`

| A default StorageClass (Showroom's PVC)
| `oc get storageclass`

| Egress to `huggingface.co` (the 4.9 GB model file, verified by sha256) and `ghcr.io` (llama.cpp image)
| The `safety-guard` pods reach `Running`

| For Module 5: an API key for the workshop's Model-as-a-Service endpoint, and egress to it (`judge.baseUrl` in `automation/argocd/values.yaml`)
| `make judge-secret` (below), then `make verify`

| An identity provider participants log in with, and their users
| `make users` creates them in Keycloak (below)
|===

Per-participant footprint: the workbench (1 to 2 cores, 2 to 4 GiB, and a 5 GiB volume), the
live monitor (about 100 MiB) and the guardrails server (about 1 GiB with Presidio). Shared: the
safety model, 2 × 16 cores and 2 × 8 to 12 GiB. Each workbench pulls a multi-GB image on first
start, so the first rollout takes several minutes per node.

== Provision

From a cluster-admin shell in a checkout of this repository:

. Set the user list in `automation/argocd/values.yaml` (`lab.users`; the default is
  `user1`..`user5` plus `presenter`, a regular account to present with). Present as a
  non-admin account: a cluster-admin sees `yes` and `200` where the guide expects `no` and `403`.
  If an existing account must be in the list anyway, name it in `lab.presenters`: `make users`
  never creates or resets it, and `make verify` skips the participant denial checks for it.
  Commit and push. Argo CD deploys from the remote, not from your checkout.
. Create the participants' Keycloak accounts (`lab.users` minus `lab.presenters`). Each gets
  its own random password, printed once at the end and stored nowhere; hand every attendee only
  their own line. A shared password would let any attendee log in as another and reach their
  tenant. Re-run to reset everyone's password.
+
[source,bash]
----
make -C automation users
----
. Deploy:
+
[source,bash]
----
make -C automation bootstrap
make -C automation status
----

`bootstrap` first refuses to run if any namespace the lab would create already exists without
this lab's label. To deploy a different branch, `make -C automation bootstrap REVISION=<branch>`:
the parent, the components and the Showroom guide all follow it.

Repeat `status` until every Application shows `Synced` and `Healthy`. The safety model takes
a few minutes on first start while it downloads and verifies the model file.

. For Module 5, give the shared judge proxy the MaaS API key: the Secret `maas-judge` in
  `{lab_namespace}`. The key is read from the environment and never printed, and it never goes
  into a participant's project: participants write the rail configurations that decide where their
  guardrails server sends requests, so a key there could be redirected to any address. Re-run to
  rotate the key. Without it, skip Module 5: Modules 1 to 4 do not need it.
+
[source,bash]
----
read -rs MAAS_API_KEY && export MAAS_API_KEY
make -C automation judge-secret
----

== Verify every cluster

[source,bash]
----
make -C automation verify
----

Every line must print `PASS`. The checks impersonate each participant and each workbench to
confirm what they may and may not do, check that every workbench is running with its auth
sidecar and that no participant project holds a copy of the judge key, that the decoy tenant `{decoy_namespace}` refuses anonymous callers, and ask the safety
model to classify an unsafe prompt from a tenant namespace. Fix any `FAIL` before participants
arrive.

Then log in once as the first and the last participant in a browser, open their workbench from the
OpenShift AI dashboard, and run the pre-flight from xref:02-details.adoc[Prerequisites and Environment].

== Day of class

* Share the Showroom URL (`oc -n {showroom_namespace} get route showroom`) and the console URL with everyone; give each attendee their own username and password privately.
* Presenter: run the lab as `presenter` with the live monitor on a second screen. Module 3's content-safety run is the moment to pause: the counters climb while the log scrolls.
* Five participants evaluating at once share four parallel slots per safety-model replica; a content-safety run then takes up to about five minutes instead of two to three.
* If a participant's monitor shows only `ERROR` verdicts, read its pod log pane first; the cause (a typo in a ConfigMap, a missing `rails.co`) is usually there.
* A stopped workbench is restarted from the OpenShift AI dashboard (*Workbenches* tab, *Start*); its files survive.
* The judge proxy spends the facilitator's MaaS key for anyone in the lab's namespaces: participants can send it any prompt for the one model it serves. Tear the lab down, or delete `maas-judge`, when class ends.
* Module 5's judge is a remote, shared endpoint: about 6 seconds per prompt alone, more when five participants run the 50-prompt cell at once. If MaaS rate-limits or slows past the guardrails proxy's 30-second timeout, prompts come back as `error` and the notebook stops at its `errors == 0` check; have participants run one at a time, or present that section.
* Anyone with the Showroom URL can read the guide; it contains no credentials. Tear the lab down when class ends.
